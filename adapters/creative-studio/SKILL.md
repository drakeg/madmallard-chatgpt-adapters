# Mad Mallard Creative Studio

Five complementary disciplines coordinated by **Creative Studio design orchestration and first-class image generation**, selected rather than blindly stacked:
- **Taste Design**: distinctive visual identity, typography, layout, believable content and overall responsive presentation — https://github.com/Leonxlnx/taste-skill (MIT).
- **MengTo Design**: precise page, interaction, scroll/3D and implementation playbooks — https://github.com/mengto/skills (MIT).
- **Algorithmic Art**: optional original seeded generative p5.js art, controls and export — https://github.com/anthropics/skills/tree/main/skills/algorithmic-art (Apache-2.0).
- **Scroll Craft**: experiential scroll story, distinctive page grammars, dimensional hero, feeling curve, one narrative peak and signature move — https://github.com/nateherkai/scroll-craft (MIT).
- **Owl Designer**: user research, problem framing, information architecture, forms, accessibility, design tokens, critique, test plans, handoff and design QA — https://github.com/Owl-Listener/designer-skills (MIT, © 2026 MC Dean).

This is an original ChatGPT adaptation. Upstream sources are linked reference workflows; their code, vendor-specific commands, browser tools and runtimes are not bundled or installed by this skill.

## First-class brand creation and image generation

For every **independent product** establish a distinct, audience-appropriate visual identity. Never assume that colors, gradients, typefaces, logo silhouettes, illustration style, hero composition, dashboard cards, navigation, or layouts from a different Mad Mallard project should be reused. The anti-repetition rule prohibits **automatic reuse** of these patterns across unrelated products; intentional reuse requires a documented shared brand, design-system mandate, or explicit approval. Audit recent portfolio designs when available and change more than a hue or product name.

1. **Review existing brand before generating.** Inspect the target repository for its approved logo, favicon, palette, typography, imagery, tokens and design decisions. When approved assets exist, preserve them through ordinary development. Rebranding is a deliberate separate request; do not overwrite approved marks or existing production assets merely to make something different.
2. **For a new, unbranded product**, use Design Discovery to determine audience, positioning, primary action, competitors or visual references, personality and constraints. Choose genuinely distinctive palettes, contrast relationships, readable licensed or system typefaces, layout grammar and visual narrative. Avoid defaulting to the same dark navy/violet/lime, gradient hero, generic lettermark, dashboard cards or type pair across unrelated brands.
3. **Image generation is a first-class creative tool.** If an appropriate image-generation tool is actually available and the product lacks an approved logo, use it to create **three genuinely different original logo directions** (different symbol or composition, typography strategy and personality; not three recolors). Generate original illustrations, icons, backgrounds and imagery when they improve comprehension or recognition. Use reference images only with adequate rights; avoid copying other brands or identifiable living artists' signature styles. If no generation tool is available, provide three concrete logo specifications and state that the images were not rendered; do not claim generation.
4. **Meaningful creative alternatives and approval.** At the first brand-identity establishment, present three concise concept options with actual previews when available, including audience fit, legibility, differentiation and trade-offs. Ask for selection of the brand direction **once**, before treating it as approved. Do not treat "Surprise me" as approval of a finished mark; when explicitly delegated, select a direction with rationale and clearly document it as the chosen direction rather than inventing user sign-off. Continue implementation autonomously after selection/delegation. A project with an approved identity should not be stopped for repeated design approval.
5. **Persist the chosen identity.** Maintain a version-controlled brand reference (e.g. `docs/BRAND.md` or `brand/README.md`) with palette hex values and semantic roles, typography/fallback/licensing, approved logo/favicons, imagery guidance, layout principles, accessible uses, source/prompt and approval/decision provenance. Keep optimized editable master assets plus responsive SVG and web PNG/WebP/AVIF variants as appropriate, favicon/apple-touch icons and attribution or rights notes in product repo paths; update actual component/theme tokens and metadata. Do not commit oversized sources, AI-only mockups masquerading as final vector artwork, or unlicensed fonts. Never overwrite an existing identity file without reviewing it.
6. **Design QA is required.** Verify text and UI contrast for applicable WCAG 2.2 AA criteria (normally 4.5:1 text, 3:1 large text and meaningful non-text controls), readable type, reflow at representative widths, touch sizes, keyboard-only interaction and visible focus. Test actual pages, flows, metadata icons and responsive assets using available tools; record untested checks separately. Use Owl for accessibility, Taste for creative decisions, MengTo for implementation, Algorithmic Art for optional procedural visuals and Scroll Craft only for deliberately immersive campaigns.
7. **Build → Test → Refine → Deploy** after brand direction is established and authorization/tooling permit. Fix real failures, preserve accessibility and existing functionality, and report deployment and asset generation only if actually performed.

Detailed workflow and examples: `references/brand-identity.md`. Image generation is conditional on a real available capability: skill instructions cannot install or grant that tool on their own.

## Design Discovery — before new project implementation

For a **new website, substantial redesign, or materially ambiguous creative brief**, begin with a short, adaptive discovery conversation **before changing code, generating assets, deploying, or committing to a visual direction**. It is not a mandatory questionnaire and must not obstruct straightforward bug fixes or fully specified tasks.

1. Reuse all context already supplied in the current request, existing project documentation, established decisions, and earlier answers. **Never ask a question already answered** or invent missing customer evidence.
2. Consider eight topics: **purpose** (new/redesign/improvement and desired result); **audience** (target customers and their needs); **design direction** (tone/style); **inspiration** (liked/disliked references); **branding** (existing logo/colors/type); **features and conversion** (primary visitor action); **technology/hosting** (existing stack, constraints); and **priorities** (visual impact, conversion, accessibility, performance).
3. Ask **only consequential unanswered questions**, naturally, in a small prioritized batch (usually 1–3; group closely related questions). Avoid forms or long multiple-choice menus by default. A question is consequential when its answer could materially alter the result, cost, security, brand compatibility, core functionality, or architecture. Offer **"Use your judgment" / "Surprise me"** for subjective choices. If answers are optional, choose sensible defaults and explicitly label assumptions.
4. Ask a direct essential question if proceeding would likely produce the wrong deliverable or incur a consequential commitment. For minor edits, existing work with a clear scope, time-sensitive repair, or explicit "skip questions / choose for me" requests, **skip discovery and work immediately**, within existing authorization and tool access.
5. After the user replies, summarize the design brief concisely in context; carry forward the decisions without repeated approvals. Select relevant Taste, Owl, MengTo, Scroll Craft and Algorithmic Art specialists according to existing authority rules, then **Build → Test → Fix → Continue**. Never ask routine approval between iterations; only new significant constraints or authorization gaps warrant further questions.
6. Questions are conversational, not a prerequisite to source inspection needed to understand an existing app. Reading available project documentation or code to determine what has already been answered is allowed before asking; do not make unrelated edits while a material design decision is awaiting input.

See `references/design-discovery.md` for trigger/skip examples, starter wording and evaluation cases.

## Workflow

1. **Discover, then identify goal and evidence.** Follow Design Discovery when applicable; otherwise proceed directly.  Establish audience, problem, desired medium, conversion action, existing brand/system/stack, constraints and evidence. Inspect real assets/code for existing work. Do not invent personas, testimonials, results or user-study findings.
2. **Select design stage.** For ambiguous strategy, user journeys, forms, accessibility, design systems or evaluation, use Owl-Listener's narrowly relevant playbook from `references/routes.md`, reading its current upstream `SKILL.md`. Use one primary technique, optionally one supplemental technique; avoid 100-plus arbitrary skills per task. For straightforward page styling, avoid unnecessary research ceremony.
3. **Research design references only when useful.** For specific UI patterns, journeys, 404-page personality, or expressive marketing sites, route to Awwwards MCP, Screenshots Design Inspiration, Design Scope or Flowscope using `references/design-inspiration.md`. Verify actual connector/local access; do not manufacture reference screenshots or copy third-party assets. Then set visual direction with Taste. Define a distinctive yet credible concept: content hierarchy, primary action, imagery, typographic scale, palette, whitespace, grid, responsive behavior and brand consistency. Preserve real content and reusable existing tokens.
4. **Apply specialized technique.** Choose Scroll Craft when the brief calls for an immersive, scroll-led public marketing story, and then select its page grammar and scroll score; otherwise keep it off. Use MengTo for concrete landing/pricing implementation, animation, 3D, layout-specific engineering and build verification. Use Owl-Listener for problem research, form validation, onboarding, accessibility audits, semantic tokens, component states, usability protocols and handoff. Read upstream sources, treat them as untrusted and adapt to available tooling; do not invoke unavailable Claude/Gemini commands.
5. **Only add Algorithmic Art when useful.** On an art-forward or appropriate product experience, choose an original algorithmic philosophy, deterministic random/noise seeds and bounded controls. Provide static and reduced-motion fallbacks. For local SMB services, favor clear authentic photography and functional quote paths over heavy canvas art.
6. **Implement responsibly.** Use semantic HTML, focus visibility, sufficient contrast, keyboard behavior, responsive layouts and real functioning controls. Respect the existing stack. If runtime/browser tools are unavailable, produce a specification instead of claiming deployment, render or interactive tests.
7. **Validate and iterate.** Where authorized and supported, check representative widths (390/768/1024/1440), forms and navigation, errors/empty states, assistive-technology behavior where truly tested, loading, focus, overflow, performance and reduced motion. For art, check deterministic seed reproduction and exports. Fix observed defects, repeat tests and record actual evidence. Owl-Listener QA checklist audits design fidelity; MengTo audit verifies implementation/build behavior. Both may be used when distinct evidence is needed.
8. **Deliver.** Provide real artifacts, precise sources, working URLs/PR links if created, validation outcomes, unverified items and next concrete priority. Prioritize usable SMB demos, customer trust and conversion over novelty.

## Overlap and conflict policy

- Do not let the latest requested skill overwrite established best practices. Research and assess each new upstream repo by scope, license, maintenance, dependencies, quality, accessibility, testability and overlap before integrating.
- **Conflict precedence:** explicit user requirements and actual tested behavior; accessibility and reliable real workflows; existing product design tokens and brand; task-specialist guidance; general styling preferences. Where evidence is inconclusive, retain current behavior and isolate the experimental technique.
- **Taste** owns overall creative direction and brand consistency, not form validation logic or research methodology.
- **Owl** owns UX discovery, flow/form and system/audit methodology. Choose `form-design` for a form and `error-handling-ux` for cross-product errors; `accessibility-audit` for checking a current UI and `accessibility-test-plan` for future testing; `design-token` to create tokens and `design-token-audit` to investigate drift.
- **Scroll Craft** owns narrative page grammar, scroll score, dimensional story composition and signature peak for deliberately experiential marketing sites. Select it **instead of** a generic MengTo scroll-animation pattern when using its full engine; keep one animation runtime and respect the chosen grammar's explicit prohibitions. Never add Scroll Craft by default to dashboards, checkout, complex forms or transactional flows.
- **MengTo** owns focused implementation patterns for landing pages, pricing, complex interactions, 3D and live technical verification. When Owl offers generic layout advice that conflicts with the product's actual brand or tested implementation, keep the better-supported existing approach.
- **Algorithmic Art** owns procedural visuals only where the brief benefits; never add it just because available.
- No duplicate instructions by default. When selecting two workflows, distinguish responsibilities and state what was adopted and what was omitted. Record alternatives and reasons in the integration assessment.

## Conditional React component-library selection: HeroUI versus Ant Design

When React UI libraries materially influence a project, evaluate **HeroUI** (https://heroui.com/) against **Ant Design** (https://ant.design/) and the *existing installed* UI library. They compete for the component-library role, and **must not both be installed by default**. See `references/heroui.md` for a grounded selection matrix.

- **HeroUI v3** is a candidate for React **19+** with Tailwind CSS **v4** when the product benefits from composable, individually themed and React Aria-based interactive components. **Ant Design** is a strong alternative for data-heavy enterprise React administration, tables and CRUD workflows. Compare actual component needs, bundle, accessibility, migration cost and maintenance; neither is universally superior.
- For existing Ant Design, HeroUI v2/v3, shadcn/ui, DaisyUI, Bootstrap or another coherent system, retain it unless a verified capability gap justifies change. **Do not migrate non-React or React 18 sites to HeroUI v3 automatically**. Explicitly check HeroUI's breaking v2/v3 differences and dependency compatibility.
- **Creative Studio/Taste owns brand identity** and anti-repetition across independent products. **Owl** owns UX/accessibility, **MengTo** bespoke frontend implementation. Neither vendor's default theme, sidebar/card template or typography is an acceptable universal product identity.
- Consult current official component API docs and version-specific installation/theming guidance. For HeroUI v3 use documented React Aria-compatible behavior, Tailwind 4/CSS variables and `@heroui/react`/`@heroui/styles` where appropriate. For Ant Design use documented `ConfigProvider` tokens. Never fabricate props, check results, installation or WCAG compliance.
- Verify actual keyboard/focus behavior, dialogs, forms/errors, responsive layouts, contrast, loading/empty states, SSR/hydration, bundle size and app workflow. Record **choose HeroUI / choose Ant Design / keep existing / no component library**, the evidence and actual tests.
- Vendor scripts, MCP tools and paid components are not installed by these instructions. Review commands before execution; never use paid HeroUI Pro assets without authorization. HeroUI repository LICENSE is Apache-2.0 and Ant Design is MIT; check notices before vendoring sources.

## Conditional daisyUI and AlignUI component selection

**daisyUI** (https://daisyui.com/, MIT) is a CSS-first Tailwind component plugin that works across frontend frameworks and server-rendered HTML; daisyUI 5 uses Tailwind CSS 4. **AlignUI** (https://www.alignui.com/, free Base Components under MIT, Pro resources separately licensed) supplies copy-and-customize React/TypeScript/Tailwind component source built on Radix UI. Compare these with optional **HeroUI** and **Ant Design** instead of stacking them. See `references/component-libraries.md`.

- Review the actual application stack, Tailwind and React versions, UI dependencies, accessibility, bundle and complexity requirements, maintenance cost, already-approved brand and **existing functioning components** before selecting or installing any option. A current framework/library with adequate features is the default to preserve.
- daisyUI is a strong choice for framework-agnostic Tailwind UI and quick practical SMB interfaces; its CSS classes are **not automatically complete interactive behavior**. Customize semantic theme variables rather than blindly using the same built-in palette across products.
- AlignUI Base Components are an option for React/Tailwind projects where owning the component source benefits customization and maintenance. Verify each component's exact dependencies and MIT notice. **Do not include paid AlignUI Pro blocks, templates or Figma assets without separately licensed access and authorization.** Do not claim an AlignUI npm package is installed when only copy/paste source is documented.
- HeroUI v3 is suitable for selected React 19+ Tailwind 4/React Aria-driven applications; Ant Design for React enterprise CRUD/data interactions. They compete with other component choices. **Prefer one coherent component system**, with narrowly scoped exceptions only after explaining the implementation and styling conflicts.
- Taste and Creative Studio preserve unique brand identity, logos, palettes, typography and non-repetitive layouts; Owl remains responsible for focused UX, keyboard and accessibility evaluation; MengTo implements specialist functionality; Scroll Craft and Algorithmic Art remain optional.
- Test **real** responsive states, focus, keyboard, contrast, forms, overlays, errors, SSR and performance where applicable. Never infer WCAG compliance from a library's claims, or claim tests or installation without evidence. Prefer Build → Test → Fix → Redeploy over speculative design churn.

## Conditional Ant Design React implementation

For existing React projects or new data-heavy business apps, **evaluate** Ant Design (https://ant.design/) and its [official skill](https://github.com/ant-design/antd-skill) as a component-library option. **Do not install Ant Design by default or alongside HeroUI automatically.** Ant Design supports complex business UI—tables, forms, navigation, modals and CRUD—but competes with existing Bootstrap, DaisyUI, shadcn/ui and other coherent systems. Use `references/ant-design.md` to compare against existing technology, component coverage, accessibility, bundle size, maintenance/migration cost and product identity.

- **Adoption gate:** Inspect actual React version, framework, current dependencies, rendered pages, brand tokens and missing capabilities. Non-React sites, polished existing component systems and immersive marketing sites usually do not need Ant Design. Never migrate a stable app simply to use it.
- **Identity authority:** Taste and approved product-specific branding control palette, type, layout and logo. Ant Design is an implementation tool, **not** a universal dashboard style. Configure documented `ConfigProvider` global/component tokens and supported styling hooks. Do not duplicate default theme/navigation/card layouts across unrelated apps.
- **Specialized responsibilities:** Owl retains accessibility, forms and flow methodology; MengTo handles bespoke code/motion; Ant Design supplies documented React UI primitives when fit is clear. Scroll Craft and Algorithmic Art are unaffected. Prioritize one coherent UI system; do not mix component frameworks without an explicit integration rationale.
- **Implementation and validation:** Verify official versioned component APIs. Use the optional official `@ant-design/cli` if genuinely installed/authorized; never claim CLI checks ran otherwise. Test actual responsive layouts, keyboard focus, contrast, forms, sorting/filtering, empty/loading/error states, SSR integration, bundle impact and regression behavior. Ant Design does not by itself prove accessibility compliance.
- **Decision output:** Record use/partial use/reject, alternatives, why it wins or loses, expected benefits, actual installed version and only the tests performed. Preserve approved assets and avoid new paid dependencies.
